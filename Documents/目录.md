# 目录

已提交版本见 `Documents/版本记录.md`。结构已由批示 017 冻结。当前正文版本是 v1.7（批示 024）。

产品需求在 `Documents/上层决策/产品/产品需求文档.md`（下称 PRD），会按批示不断完善。现在只设两个部门：研发部、市场部。`上层决策`、`下发工单` 是文档分类，不是新的部门。上层指你，下发指发给子 agent。

## 权威顺序

1. `Documents/上层决策/产品/` 里的 PRD
2. `Documents/上层决策/批示/` 里已写入的批示
3. 各部门规格中状态为「已确认」的条款
4. 状态为「建议」的条款，只供审阅

你只做最上层批示。聊天记录、`Documents/上层决策/待批示/`、`Documents/上层决策/存档/` 不是需求。每一级的计划、执行和结果以该级文档为准，不依据对话。

上一级把下一级要完成的事写成工单。工单必须引用上一级依据：最上层是批示编号，再往下是上一张工单。没有工单，下一级不改仓库。命令不得超出上一级文档。子部门由其上一级部门负责，不把执行细节跳级送到最上层。

现在最上层的下一级是研发部和市场部。以后某部门内设子部门，工单写在该部门自己的 `下发工单/` 里，由该部门管理。结果写在同一张工单上。只有上一级文档没有覆盖、或要改 PRD 的事项，才逐级写入待批示并停工，直到需要你批示。

## 版本

会改的正文使用 `v主.次`。一次批示改了正文，次版本加 1。一个阶段的范围冻结时，主版本加 1，次版本归零。批示、待批示和存档不参与版本号。

`Documents/版本记录.md` 只记录已经 commit 成功的版本，并写上提交号。你在对话里要求 commit 且这次提交成功之后，才追加该版本。提交前不写入。已提交的是 v0.1、v0.2、v1.0、v1.1、v1.2、v1.3、v1.5 和 v1.7。v0.3 从未提交成功，不记。v1.4 与 v1.5 写在同一次提交里，只记 v1.5。v1.6 与 v1.7 写在同一次提交里，只记 v1.7。

版本更新的当次回复写明版本号、改了哪些文件、为什么改。你明确说提交之前，不做 Git 提交。

## 文件夹

| 路径 | 谁用 | 放什么 |
| :--- | :--- | :--- |
| `Documents/版本记录.md` | 两个部门一起读 | 只记已经 commit 成功的版本 |
| `Documents/上层决策/产品/产品需求文档.md` | 两个部门一起读 | 要做的产品，即 PRD。维护规则见同文件夹 `00-维护.md` |
| `Documents/上层决策/批示/` | 两个部门一起读 | 已作出的决定。部门和子 agent 按这里执行 |
| `Documents/上层决策/待批示/` | 你和负责人 | 还没决定的说明，一件一份 |
| `Documents/上层决策/存档/` | 你和负责人 | 已经批完的说明留底，不拿来执行 |
| `Documents/研发部/` | 研发子 agent | 状态机、接口、分系统规格、研发任务书、待定项 |
| `Documents/市场部/` | 市场子 agent | 宣传规则、市场任务书、待定项 |
| `Documents/下发工单/` | 最上层的下一级 | 你的批示转成的工单。一张工单写命令和结果。当前按部门分子文件夹 |

你批示之后，待批示文件移到 `Documents/上层决策/存档/`。该批示若要下一级交付，直接上一级写成工单并交给下一级执行，不就已有文档里的细节再请你决定。结果写回该工单，并在回复里汇报。

研发部不写宣传文案。市场部不改产品规格，不把调查推断写进 PRD。市场材料里的能力必须能指到 PRD，或指到研发部已经完成的交付物。

在你书面同意某一份任务书之前，不派子 agent 写代码、不建 UE5 工程、不采购或接通外部模型服务，也不制作小视频或 PPT。Demo 有可观看的实现之前，市场部不制作宣传材料（批示 002）。批示 018：研发第一阶段先不开工；Demo 前只做产品定义调查，证据用公开信息。

## 日期

批示、待批示、存档和工单的文件名、文内「日期」都写到秒。文内用 `YYYY-MM-DD HH:MM:SS`。文件名把时刻接在日期后面：`YYYY-MM-DD-HHMMSS`。时区用本地时间，现在是 UTC+9。来源报道里的日期不改。已经写过的文件，秒用它第一次进入 git 的提交时间，不另编。
