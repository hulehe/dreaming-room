# 目录

版本：v0.1 · 2026-11-13 · 批示 005

产品需求在 `Documents/产品/`（下称 PRD），会按批示不断完善。现在只设两个部门：研发部、市场部。`产品` 是文档分类，不是第三个部门。以后要再拆小组，另写批示。

## 权威顺序

1. PRD 里的产品定义
2. `Documents/批示/` 里已写入的批示
3. 各部门规格中状态为「已确认」的条款
4. 状态为「建议」的条款，只供审阅

聊天记录不是需求。你的决定写入 `Documents/批示/` 之后才派工，也才改 PRD。负责人给你的说明写入 `Documents/汇报/`，汇报本身不构成批示。规格与 PRD 冲突时，停止对应部门的工作并写汇报。

## 版本

会改的正文使用 `v主.次`。现行文件只有一份，文件头写着版本、日期和批示。台账在 `Documents/版本记录.md`。批示和汇报写入后不改，不参与版本号。

- 现在是 **v0.1**。一次批示改了正文，次版本加 1。一个阶段的范围冻结时，主版本加 1，次版本归零。
- 版本更新的当次汇报必须写明：新版本号、改了哪些文件、为什么改。
- 版本更新之后必须提示你 commit。你明确说提交之前，不做 Git 提交。

## 文件夹

| 路径 | 谁用 | 放什么 |
| :--- | :--- | :--- |
| `Documents/产品/` | 两个部门一起读 | PRD。完善规则见该文件夹 `00-维护.md` |
| `Documents/版本记录.md` | 两个部门一起读 | 每一版改了什么 |
| `Documents/研发部/` | 研发子 agent | 状态机、接口、分系统规格、研发任务书、研发决策 |
| `Documents/市场部/` | 市场子 agent | 宣传材料规则、市场任务书、市场决策 |
| `Documents/汇报/` | 负责人写给你 | 阶段说明、待你拍板的事项 |
| `Documents/批示/` | 你写的决定 | 同意、否决、改口 |

研发部不写宣传文案。市场部不改产品规格，不把调查推断写进 PRD。市场材料里的能力必须能指到 PRD，或指到研发部已经完成的交付物。

在你书面同意某一份任务书之前，不派子 agent 写代码、不建 UE5 工程、不采购或接通外部模型服务，也不制作小视频或 PPT。Demo 有可观看的实现之前，市场部不制作宣传材料（批示 002）。
